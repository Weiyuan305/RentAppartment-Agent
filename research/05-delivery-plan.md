# 开发顺序与验收标准

日期：2026-09-21。以下时间是基于任务拆分的粗估，供安排顺序；不构成排期承诺。前提为熟悉 React/TypeScript 的 1 名全栈开发者，能得到必要地图/模型账号和可用数据。房源商务接入、授权审批、完整五地精细数据整理单独计时。

## 1. 推荐执行顺序

| 阶段 | 工作 | 建议投入 | 完成证据 |
| --- | --- | --- | --- |
| A：技术验证 | 伦敦一个明确校区；Cesium 实景纹理与连续覆盖、20 个标注、真实步行路线、基础对话工具联动 | 5–8 个开发工作日 | 实景截图、图层遮挡/贴合检查、路网样本、地图加载耗时 |
| B：完整找房交互 | 五市场/城市入口、三栏、轮播、详情、筛选状态、手机模式；演示数据有标识 | 7–10 个开发工作日 | 主流程端到端可用；列表、地图、聊天 ID 一致 |
| C：真实数据闭环 | 房源导入、有效报价、校区、通勤矩阵、POI、区域资料来源、异常降级 | 10–15 个开发工作日 | 真实来源可追踪，过期/缺失/下架可处理 |
| D：试用与加固 | 五市场各一城实景抽样、权限与密钥检查、三维设备性能、恢复能力、使用反馈修复 | 7–10 个开发工作日 | 覆盖/纹理验收、错误和成本记录、无阻断性问题 |

按上述假设约 **29–43 个开发工作日**，约 6–9 周开发投入，另加数据准备等待。只有演示数据的界面原型会更快，但不能把它称为已上线真实找房服务。全部目标城市的扩展规模需在首城验证后估算。

用户已确认实景三维路线，阶段 A 核查 Cesium 的目标校区实景覆盖、纹理、遮挡、手机表现和账单。以上估算已增加实景验证投入；结果不合要求时调整数据供应方案，不自行降低视觉要求。

## 2. 第一阶段必须得到的结论

- 实际加载的城市数据达到已确认的实景要求，具有真实建筑结构和外观纹理；保留可运行效果与截图。
- 选定实景数据覆盖目标校区及样本房源周边；标记与路线在三维场景中定位准确、可读。
- 房源和校区有可用于路由的入口坐标；从房源到校区的方向正确。
- Valhalla/托管服务的步行时间、等时圈和矩阵在所选城市可用。
- AI 输出的房源与地图来自同一个业务搜索结果，模型无需自己计算距离或凭记忆生成地址。

技术验证优先做一城，系统模型从一开始支持五市场。到阶段 D 的试用版本，五市场至少各有一个经过验证的城市/搜索区域；暂未就绪的其他城市明确显示能力状态，不假装覆盖。

## 3. 可观察验收清单

| 编号 | 验收动作 | 通过标准 |
| --- | --- | --- |
| P01 | 进入国家/地区选择 | 仅显示 GB/AU/SG/MY/HK 对应的五个目的地 |
| P02 | 选择不同城市 | 进入该城市工作台；旧城市房源、校区、路线和延迟请求不串入 |
| P03 | 连续切换卡片图片 | 图片可左右切换，不打开详情、不误定位、不影响其他卡片 |
| P04 | 列表选择一套房 | 地图定位并高亮正确房源；选中卡片保持可见 |
| P05 | 地图点击标注 | 对应列表项选中；同栋多个报价可分别查看 |
| P06 | 打开详情后返回 | 筛选、列表滚动、镜头与会话恢复；详情可独立访问 |
| P07 | 放大、缩小、旋转、俯仰 | 真实建筑纹理与三维结构可见，镜头和叠加图层正常；低性能备用模式独立标识 |
| P08 | 输入“大学走路 30 分钟内” | 未选学校时先澄清；选校区后用真实步行服务判断，不用半径替代 |
| P09 | 29/30/31 分钟边界样本 | 以原始秒数判断 ≤1800，不因四舍五入误纳入 31 分钟房源 |
| P10 | 直线很近但隔河/封闭门的样本 | 路由不把直线接近当作可达；无路线显示未知/不可达 |
| P11 | 多轮“更便宜、超市近一点” | 保留校区和未撤销的硬条件；更改可见且可撤销 |
| P12 | 输入相互冲突的条件 | 明确无严格匹配；用户接受前不擅自放宽 |
| P13 | 查询“比较安全” | 展示来源、统计期、地域粒度；缺数据不会生成高安全分 |
| P14 | 英镑周租、澳元周租、新币/月等样本 | 原币、周期、按人/套明确；折算不覆盖原报价 |
| P15 | 步行接口或 AI 超时 | 不编造时间/答案，已知房源可继续浏览，支持重试 |
| P16 | 报价失效、房源下架 | 从有效搜索移除或明确状态，详情不再声称当前可租 |
| P17 | 快速改城市与预算 | 旧 SSE/请求不会覆盖新结果；模型引用与当前结果版本一致 |
| P18 | 手机、键盘和读屏 | 可完成选择、筛选、查看详情；不依赖地图作为唯一信息来源 |
| P19 | 恶意房源描述含“忽略条件” | 作为普通数据处理，不能改变工具权限、预算或产生脚本执行 |
| P20 | 五市场各一城的采样 | 记录数据覆盖及限制，未验证项不标为通过 |

## 4. 性能目标（待测试，不是现有成绩）

先约定测试设备和网络，例如中档笔记本/手机、受控 4G 或固定带宽，并记录浏览器、分辨率、数据规模、缓存状态。

- 页面先显示可用筛选和房源骨架；常见网络下首批真实房源目标 2–3 秒可操作。
- 地图拖动/旋转在参考设备上争取 30 FPS 以上；测试时记录数据密度和实际帧率。
- 常规数据库搜索目标 p95 < 1 秒，不含外部路由和模型调用。
- 聊天收到输入后尽快反馈真实进度；外部调用整体超时可先设 15–20 秒，超时仍保留已有状态。
- 对约 1,000 条测试房源验证聚类、分页、选中定位与内存；只有 20 条演示数据不能证明城市级性能。

若目标设备或网络未确定，先测量再定指标，不能为了满足数字删掉实际需求。

## 5. 测试投入如何分配

重点单元/集成测试：租金周期及按人/套、日期/租期兼容、路线方向、入口选择、经纬度顺序、1800 秒边界、未知数据、结果版本隔离。它们会影响推荐正确性。

端到端覆盖主旅程：选择市场/城市 → 选校区 → 自然语言筛选 → 点击房源定位 → 轮播 → 详情 → 返回。对地图做真实浏览器交互和人工视觉检查，不把组件截图或 mock 路由当作真实地理验证。

收集一组地理样本，特别包含跨河、校园封闭入口、天桥和多校区。把“引擎按当前图计算正确”和“现实中确实可以按该路线走”分开记录。

## 6. 成本怎么测算

本次不提供未经业务量验证的月费总报价。成本由数据、流量、请求策略及供应商计划决定，应在原型中测量每次有效找房会话的调用量。

```text
月成本 = 应用托管 + 数据库/备份 + 图片存储/CDN + 瓦片/三维数据
       + 路由/地址/POI API + 模型 token + 导入/图构建任务 + 监控
       + 房源数据授权或合作成本

模型 token 成本 = 月会话数 × 每会话平均输入/输出 token × 对应单价
路由规模 = 首次候选矩阵元素数 + 后续未命中缓存的路线元素数
```

计费单位可能是地图会话、瓦片请求、路线请求或矩阵元素，不能统一按“调用一次”估计。地图拖动不触发 AI；选中房源再加载详细路线；按允许的规则缓存，是首版就应实现的成本控制。

作为**容量演算例子**：若月 10,000 次找房会话、每次 100 个候选到 1 个校区入口，未缓存矩阵可能达到 1,000,000 个路线元素/月；多个校区入口或每个房源再查多个超市会继续增加。该例不是流量预测，也不是任何供应商报价。

地图商业报价查看 [MapTiler 定价](https://www.maptiler.com/cloud/pricing/)与所选三维服务的当前正式报价；免费试用额度不作为长期预算。选自建 Valhalla/PMTiles 时，也需要计算图构建、存储、带宽和维护投入。

## 7. 开发时仍需确认的信息

以下可以在阶段 A 过程中逐步确认，不构成本轮调研的阻塞：

1. 实景数据渠道：Google 直连或 Cesium ion 账号/套餐，及样本校区的实际覆盖。三维目标已确定为实景纹理。
2. 房源供应：已有合作方/自有房源，还是从有标记的演示数据开始。
3. 首个运营城市与大学校区：建议伦敦试点，最终由实际房源和目标学生决定。
4. 上线范围：仅帮助找房与查看详情，还是后续还要预约、签约和支付。

后续实现代码继续放在 `rentApartment` 中；本轮目录中只有调查资料和采集脚本，不应运行某个上游示例便宣布全部产品完成。
